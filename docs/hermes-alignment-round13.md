# Hermes 对齐第 13 轮 — 任务处理细节：验收契约 × 冻结输入 × 预算优先级

> **状态（2026-11-23）：已落地。** 对照基线 hermes `88a1c1f4b1`（2026-11-22，
> 与本轮之间 agent 核心无新变更——最新 HEAD `31a161a6d2b` 的 400 个新提交里
> 只有 14 个落在 agent 侧，且全部是 profiles / kanban / release 相关，
> 任务主循环未变）。因此本轮不再找「hermes 新能力」，而是把 v23–v28 压测里
> **反复出现、且已被证明不是随机波动**的失败类，逐条做成确定性检查。

## 一、取证：v23–v28 的失败是不是系统性问题

看 6 轮压测的失败清单，去重后只剩 7 个类，每一类都在 ≥2 轮里重复出现：

| # | 失败形态 | 出现轮次 | 当时是否有确定性检查 |
|---|---|---|---|
| 1 | 任务写「必须交付（缺一不可）」的产物没生成，回复仍说「全部完成」 | v26 T4/T9、v27 T8/T10、v28 T1/T4 | 部分（只查存在性） |
| 2 | 自测断言数 < 任务写明的「至少 8 个断言」 | v26、v27、v28 多任务 | **无** |
| 3 | README 写了但只有一句话，任务写「≥300 字节」 | v28 T1–T9 | **无** |
| 4 | 任务写「冻结夹具 / 禁止修改」，模型改了夹具让测试变绿 | v26 多处 | **无**（完全静默） |
| 5 | 自写测试的期望值本身错（与任务示例冲突） | v28 T4、v27 T10 | 仅提示词层（弱） |
| 6 | 80% 轮次提醒说「停止验证」，模型带着红测试 / 缺产物收尾 | v28 T4（3 次跑全在 50 轮耗尽） | 提醒存在但**顺序错误** |
| 7 | 任务规格细节读错（MIME 边界尾空格、DER universal tag） | v28 T4/T5 | 纯模型能力，不立项 |

结论：**1–4、6 是系统性问题**——共同特征是「验收标准只存在于任务文本里，
而系统的完成判定只看模型措辞 + 文件是否存在」。模型只要说「完成」，
任何写明的量化门槛、只读约束都不会被核对。第 5 类用提示词层处理
（`<spec_fidelity>`），第 7 类属模型能力，不做工程掩盖。

## 二、落地项

### GAP-R13-1 验收契约：存在性 → 存在性 + 量化门槛（P0）

`packages/agent/src/deliverable-contract.ts`：

- `DeliverableSpec` 新增 `minBytes` / `minAssertions`。
- `MIN_BYTES_RE` 覆盖 `≥300 字节` / `至少 300 bytes` / `300 字节以上`；
  `MIN_ASSERTIONS_RE` 覆盖 `至少 8 个断言` / `≥8 assertions` / `断言数 ≥ 8`。
- **阈值归属**用「同一句内最近的前置文件 token」，不是固定窗口：
  真实任务文本里阈值写在细则行（`3）test_x.py：…至少 8 个断言`），
  固定窗口会绑错文件。句读边界（`。；;!\n` + 英文 `.`+空白）阻断跨句绑定。
  阈值归属扫描用**全部**文件 token（含未通过交付意图过滤的裸名）——
  细则行的文件名本身不含交付动词，但阈值必须归到它。
- `evaluateDeliverables(specs, { readFile })` 返回结构化 issue：
  `missing` / `undersized` / `under_asserted`。不可读按缺失处理（fail-closed）。
- `countAssertionLines` 与压测 harness **完全同口径**
  （`ASSERT_LINE_RE` / `ASSERT_SKIP_LINE_RE` 逐字一致），
  避免「产品侧算 8 个、harness 算 6 个」的口径分裂。

### GAP-R13-2 冻结输入保护：快照 → 比对 → 归档 → 还原（P0）

- `extractFrozenInputs`：只在**冻结信号所在句子**收集文件
  （`冻结夹具/禁止修改/只读/frozen fixture/read-only`），
  交付物清单不会被误登记。
- 冻结输入同时从交付物契约中排除——否则它们在命令行用法里再次出现时
  会被当成必交产物（v28 T1 实证：`config.toml` 曾被误登记）。
- `snapshotFrozenInputs` 在回合开始记录 sha256 + 原始内容
  （>1MB 只记哈希，不占内存）。
- 回合结束 `findFrozenMutations` 检出 `modified` / `missing`：
  **先归档改动版本**到 `workspace/frozen-archive/`（不销毁痕迹），
  **再原子还原原始内容**（`atomicWriteFileSync`），然后由续跑指令
  要求模型改实现/改断言，不许再动夹具。
- 末轮仍未解决时，footer 如实列出「被修改」事实。

### GAP-R13-3 预算优先级：80% 提醒从「停止验证」改为有序清单（P0）

旧文案「立即停止新的探索/调查/**验证**工作」与测试红门直接冲突：
模型按提醒跳过验收，带着红测试收尾（红门会拦，但白耗一轮）。
`buildWrapUpNotice`：

- 确定性算出当前仍缺失的必交产物并逐条列出；
- 给出固定执行顺序「① 写缺失的必交文件 → ② 跑验收/测试命令确认退出码 0
  → ③ 收尾汇报」；
- 明确「不要带着红测试收尾，也不要因为接近上限就跳过验收」。

### GAP-R13-4 规格保真提示（P1）

`system-prompt.ts` 新增 `<spec_fidelity>`：任务示例/期望值/硬指标是权威
验收标准；自写测试只是假设，与任务示例冲突时**以任务示例为准**；
冻结输入绝不修改；「缺一不可」的产物必须逐个落盘。

### GAP-R13-5 收尾 footer 如实陈述（P0）

回合末 `buildAcceptanceFooter` 逐条列出未达标项（缺失 / 字节不足 /
断言不足 / 冻结被改），并声明「请勿据此认为任务已全部完成」。
此前只有「声称了但不存在」有 footer，**模型只字未提的必交产物在收尾时完全静默**
（v28 T4 `report.json` 即此形态）。

## 三、文案抽离

`packages/agent/src/acceptance-notice.ts` 把三类文案（续跑指令 / footer /
80% 提醒）做成纯函数并加单测。理由：这些措辞是产品行为的一部分——
弱模型对「停止验证」与「先补文件再验收」的响应差异很大，
内联模板重构时极易被悄悄改掉，单测直接锁定关键指令。

## 五、与 hermes 的差异

- hermes 的 kanban `artifacts=[...]` 是**任务创建时显式传入**的结构化清单；
  EvoClaw 没有 kanban 入队面，只能从任务文本推断。因此本轮的阈值/冻结
  抽取一律**保守**：只在任务文本出现明确信号（交付动词、`≥N 字节`、
  `至少 N 个断言`、`冻结/禁止修改`）时启用，无信号零成本、零误报面。
- hermes 用 `ArtifactPreservationError` 直接**阻止**完成；EvoClaw 选择
  「归档 + 还原 + 续跑指令」——单用户本地信任域下，硬阻断会让模型卡死，
  而还原原始内容已经消除了「改夹具让测试假绿」的实际危害。
- hermes 的断言计数在 pytest 运行结果里；EvoClaw 没有统一的测试运行器抽象，
  改为静态行计数，且**与压测 harness 同口径**（harness 就是验收方）。

## 六、缓做（附理由）

| 项 | 理由 |
|---|---|
| 拦截 `file_write` 直接写冻结路径 | 需要 per-session 契约注册表（工具层拿不到本轮任务文本）；检测+还原已消除危害，且保留「模型确实认为夹具有问题」的申诉通道 |
| 验收失败时强制续跑（无视预算） | 与 token 预算/轮次上限冲突；末轮 footer 已保证用户看到事实 |
| 任务示例的自动 oracle（把示例输入/输出变成可执行断言） | 需要按任务类型分类的解析器，收益不确定；先用 `<spec_fidelity>` 提示词层观察 |
| `coding-context.ts` 接线 | 压测目录是独立 standalone 工作区，`detectProjectFacts` 全部返回空——接线无收益。真实仓库任务出现痛感再立项 |
